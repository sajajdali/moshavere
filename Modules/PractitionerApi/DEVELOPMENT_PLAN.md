# برنامه توسعه API اپلیکیشن پزشکان و مشاوران

این سند مرجع اصلی تحلیل، تصمیم‌ها، فازبندی، وضعیت اجرا و نتایج تست‌های
`PractitionerApi` است. فایل‌های نمونه داخل `local-input/practitioner-app` صرفاً
مرجع محصول و رابط کاربری هستند؛ قرارداد نهایی API را پیاده‌سازی Laravel، ساختار
Tenant پروژه، Sanctum و Swagger همین ماژول تعیین می‌کنند.

## اصول قطعی پروژه

- تمام endpointها روی Tenant جاری و دیتابیس همان Tenant اجرا می‌شوند.
- شناسایی Tenant باید پیش از احراز هویت و اجرای منطق API انجام شود.
- احراز هویت اپلیکیشن با Laravel Sanctum و Bearer Token است.
- فقط کاربر فعال، پزشک/مشاور فعال و دارای `app_access` اجازه ورود و ادامه کار دارد.
- مسیر پایه نسخه اول `/api/practitioner/v1` است.
- Swagger هم‌زمان با کد توسعه می‌یابد و قرارداد واقعی اپ Android و iOS است.
- Swagger باید یک سند جامع، خودکفا و قابل استفاده برای تولید/پیاده‌سازی کلاینت باشد؛
  برنامه‌نویس Flutter یا هر کلاینت دیگری نباید برای فهم قرارداد، خطاها یا قواعد هر
  endpoint به خواندن کد Laravel یا پرسیدن سؤال تکمیلی نیاز داشته باشد.
- قالب پاسخ‌ها، validation و exceptionها مطابق استاندارد Laravel و پروژه باقی می‌ماند.
- منطق نوبت، تماس، گزارش، کیف پول و تسویه در ماژول مالک آن باقی می‌ماند؛
  `PractitionerApi` فقط لایه HTTP و هماهنگ‌کننده سرویس‌ها است.
- زمان‌ها ISO-8601 همراه offset برگردانده می‌شوند. تاریخ شمسی صرفاً مقدار نمایشی است.
- مبالغ عدد صحیح و برحسب تومان، مدت تماس برحسب ثانیه و محاسبات مالی برحسب دقیقه است.
- مجاز بودن عملیات حساس را سرور در `actions` اعلام می‌کند و اپ قانون تجاری را تکرار نمی‌کند.
- عملیات مالی و حساس باید transaction-safe، قابل audit و در صورت لزوم idempotent باشند.
- پزشک فقط داده‌ها و نوبت‌های مجاز خود در Tenant جاری را مشاهده یا تغییر می‌دهد.

## قرارداد عمومی

پاسخ تکی موفق:

```json
{
  "data": {}
}
```

پاسخ فهرست صفحه‌بندی‌شده از Laravel Resource:

```json
{
  "data": [],
  "links": {},
  "meta": {}
}
```

خطای validation و exceptionها مطابق استاندارد فعلی پروژه/Laravel هستند:

```json
{
  "message": "اطلاعات واردشده معتبر نیست.",
  "errors": {
    "mobile": ["شماره موبایل معتبر نیست."]
  }
}
```

کدهای اصلی HTTP شامل `200`، `201`، `202`، `204`، `401`، `403`، `404`،
`409`، `422`، `423`، `429` و `503` خواهند بود. Swagger هر endpoint باید پاسخ‌های
واقعاً قابل وقوع همان endpoint را مستند کند.

## استاندارد اجباری Swagger و قرارداد کلاینت

Swagger/OpenAPI منتشرشده مرجع قطعی قرارداد API است. توضیح شفاهی، فایل sample و کد
بک‌اند نباید حاوی قاعده ضروریِ مستندنشده‌ای باشند. در هر فاز، موارد زیر باید برای
تک‌تک endpointهای اضافه یا تغییریافته ثبت شوند:

- هدف endpoint، نقش مجاز، نیاز به Tenant و نیاز به Sanctum token
- method، URL، headerهای اجباری و اختیاری و Content-Type
- path، query و body parameterها با نوع، format، nullable بودن، مقدار پیش‌فرض و enum
- تمام validationها شامل حداقل/حداکثر طول، بازه عددی، regex، وابستگی بین فیلدها و
  شرط اجباری‌شدن هر فیلد
- schema کامل پاسخ موفق و توضیح معنای همه فیلدها، واحدها و nullable بودن آن‌ها
- نمونه واقعی درخواست و پاسخ برای سناریوی موفق
- همه status codeهای قابل وقوع و schema و نمونه پاسخ هر خطا
- کد یا دلیل تجاری پایدار برای خطاهایی که کلاینت باید بر اساس آن رفتار مشخصی نشان دهد
- شرایط دقیق ایجاد خطا مانند غیرفعال‌بودن پزشک، پایان اعتبار OTP، قفل، نبود گزارش،
  غیرمجازبودن عدم حضور، تسویه تکراری یا در دسترس نبودن VoIP
- رفتار idempotency، retry، rate limit و headerهای مرتبط در endpointهای مربوط
- pagination، filter، sort و رفتار درخواست با صفحه یا فیلتر نامعتبر
- فرمت زمان، timezone، تاریخ نمایشی، واحد مدت، واحد مبلغ و قواعد گردکردن
- شرح stateها و transitionهای مجاز نوبت، تماس، گزارش و تسویه
- تعریف `actions`، معنای `allowed` و دلیل غیرمجاز بودن هر action
- اثر جانبی عملیات؛ مانند ابطال token، ثبت تراکنش، مسدودشدن تماس یا ارسال اعلان
- نسخه API، deprecation policy و هر تغییر ناسازگار با نسخه قبل

### مستندات عمومی داخل Swagger

علاوه بر endpointها، صفحه اصلی Swagger باید این موارد را توضیح دهد:

- روش تعیین Tenant و دامنه صحیح درخواست
- روش ورود OTP و استفاده از Bearer Token در Sanctum
- فرمت عمومی پاسخ‌ها، validation و exceptionها
- جدول status codeها و خطاهای مشترک
- سیاست token، logout، دستگاه‌ها و دسترسی هم‌زمان
- محدودیت‌های OTP و rate limit
- قرارداد مشترک زمان، مبلغ، مدت و pagination
- چرخه وضعیت نوبت و پیش‌شرط عملیات حساس
- روش ارسال `Idempotency-Key` و رفتار retry
- ملاحظات امنیتی نمایش اطلاعات بیمار
- اطلاعات محیط‌ها و base URLهای قابل استفاده

### معیار پذیرش Swagger

هر بخش تنها زمانی مستندشده محسوب می‌شود که:

1. OpenAPI تولیدشده بدون خطای ساختاری validate شود.
2. تمام routeهای همان فاز در Swagger دیده شوند.
3. نمونه پاسخ‌ها با خروجی واقعی Feature Test منطبق باشند.
4. همه شاخه‌های خطای شناخته‌شده در responses ثبت شده باشند.
5. schemaها فیلد مبهم، بدون نوع یا بدون توضیح واحد نداشته باشند.
6. یک توسعه‌دهنده کلاینت بتواند فقط با Swagger جریان موفق و خطا را پیاده‌سازی کند.
7. Swagger UI اجرا شود و درخواست‌های قابل تست آن روی Tenant آزمایشی بررسی شوند.

اگر در زمان توسعه حالت یا خطای جدیدی کشف شود، ابتدا یا هم‌زمان با کد به Swagger
اضافه می‌شود. کشف خطای مستندنشده به معنی ناقص بودن همان بخش است.

## نقاط نیازمند تأیید مالک محصول

این سؤال‌ها باید پیش از رسیدن به فاز مربوط پاسخ داده شوند؛ سؤال جدید نیز همین‌جا ثبت
می‌شود تا تصمیم‌ها گم نشوند.

1. `[تصمیم فعلی]` Sanctum token نود روز اعتبار دارد و logout فقط دستگاه جاری را خارج می‌کند.
2. `[تصمیم فعلی]` ورود هم‌زمان روی چند دستگاه مجاز است؛ ورود مجدد با شناسه همان نصب،
   token قبلی همان نصب را باطل می‌کند.
3. `[تصمیم فعلی]` cooldown برابر 60 ثانیه، اعتبار OTP برابر 120 ثانیه، حداکثر تلاش
   اشتباه 5 بار و قفل موقت 15 دقیقه است.
4. `[تصمیم فعلی]` فقط نوبت‌ها و گزارش‌های همان پزشک برای بیماری که سابقه نوبت
   غیرلغوشده با او دارد نمایش داده می‌شود؛ سوابق پزشکان دیگر افشا نمی‌شود.
5. `[تصمیم فعلی]` فرمول موجود محصول مبنا است: ثانیه‌های پاسخ‌داده‌شده با سربار اتصال
   تا سقف رزرو جمع، دقیقه رو به بالا و مبلغ بازگشت به نزدیک‌ترین ۱۰۰۰ تومان گرد می‌شود.

   اصلاح پس از تسویه فقط از جریان مستقل مدیر کل انجام می‌شود.
7. `[تصمیم نسخه ۱]` FCM برای wake-up/notification کافی است و اپ سپس
   `GET /calls/active` را می‌خواند؛ چون PBX رویداد شروع زنگ جداگانه نمی‌فرستد، فعلاً
   WebSocket منبع داده تازه‌ای ندارد. نیاز sub-second پس از تست واقعی موبایل بازبینی می‌شود.
8. `[تصمیم فعلی]` ورود تستی به‌صورت پیش‌فرض خاموش است؛ فقط هنگام فعال‌بودن در Tenant،
   کد ثابت 1234 بدون پیامک و بدون شرط app_access شخصی استفاده و در پاسخ نمایش داده می‌شود.

- تست‌های API پزشک و OTP شامل ۳۳ تست و ۳۳۱ assertion موفق شدند؛ محاسبه، Wallet،
  audit، rollback، پایان بازه، سقف دقیقه، مالکیت و ارسال تکراری پوشش داده شدند.
- هر دو operation و پاسخ‌های 200، 404 و 422 با واحد تمام فیلدها در Swagger ثبت شدند.

### ۱۴۰۵/۰۶/۲۳ — تکمیل فاز ۹: گزارش روزانه

- endpoint `GET /reports/daily` با scopeهای `today`، `date` و `last_7_days` ایجاد شد؛
  تاریخ مشخص فقط با قالب میلادی `Y-m-d` پذیرفته می‌شود.
- گزارش فقط نوبت‌های آنلاین/تلفنی غیرلغوشده پزشک جاری را از سرویس گزارش مالی موجود
  می‌خواند و timezone تنظیمات Tenant را در بازه و پاسخ رعایت می‌کند.
- جمع بازه و تفکیک روزانه شامل نوبت، بیمار منحصربه‌فرد، زمان رزرو، تماس ورودی/خروجی،
  پاسخ/بی‌پاسخ/زودهنگام، نتیجه تماس، زمان خام و مالی و تمام ستون‌های مالی CSV است.
- مقادیر مالی نهایی‌شده و در انتظار جدا هستند و مبلغ ناخالص، بازگشت قطعی/پیشنهادی،
  خالص، سهم پزشک و سود مجموعه با واحد `TOMAN` برگردانده می‌شوند.
- بازه هفت‌روزه همیشه هفت ردیف مرتب دارد و روز بدون داده با ساختار کامل و مقادیر صفر
  نمایش داده می‌شود تا رسم نمودار کلاینت نیازمند حدس یا پرکردن تاریخ نباشد.
- migration تازه‌ای لازم نبود. تست‌های API پزشک و OTP شامل ۳۵ تست و ۳۶۴ assertion
  موفق شدند؛ امروز، تاریخ مشخص، هفت روز، جمع مالی/تماس و ورودی نامعتبر پوشش داده شدند.
- schema تمام ستون‌ها و پاسخ‌های 200 و 422 به‌صورت دقیق در Swagger ثبت شدند.

### ۱۴۰۵/۰۶/۲۳ — فاز ۱۰: پایداری و آماده‌سازی انتشار

- endpoint `PATCH /devices/current` برای ثبت، چرخش و حذف FCM token همان نصب ایجاد شد؛
  lookup هم‌زمان به user، شناسه نصب و در درخواست واقعی به access token جاری محدود است.
- اعلان FCM یادآوری نوبت پزشک پس از ارسال reminder موجود و اعلان نتیجه تماس پس از
  commit گزارش PBX اضافه شد. payload شامل type، appointment_id، call_id و link است.
- تصمیم نسخه ۱ عدم استفاده از WebSocket است: FCM اپ را بیدار می‌کند و
  `GET /calls/active` منبع حقیقت است؛ گزارش PBX نیز نتیجه قطعی تماس را اعلام می‌کند.
- تست مالکیت همه منابع، عدم افشای رکورد بیگانه با 404، ability و app_access و جلوگیری
  دامنه مرکزی پوشش امنیت Tenant/authorization این نسخه هستند.
- تست سقف query برای dashboard و daily report اضافه شد. این تست یک N+1 واقعی را پیدا
  کرد: گزارش ۸ نوبت ۳۱۱ query داشت؛ گزارش موبایل به query فقط‌خواندنی eager-loaded
  تغییر کرد و دیگر هنگام GET، snapshot مالی را mutation نمی‌کند.
- collection قابل import در Postman و راهنمای staging/release شامل HTTPS، queue،
  Firebase، امنیت SIP، test login، کدهای خطا و سناریوهای release ایجاد شدند.
- تست‌های خودکار API در وضعیت فعلی ۳۸ تست و ۴۱۸ assertion است؛ تست واقعی Android/iOS، permission،
  حالت background/terminated و delivery سرویس Firebase به build و محیط staging اپ
  نیاز دارد و تنها مورد باز فاز ۱۰ است.

### ۱۴۰۵/۰۶/۲۳ — بازبینی نهایی قرارداد و سرور محلی

- تست OpenAPI علاوه بر endpointهای کلیدی، نسخه 3.1، security scheme و وجود response
  مستند برای تمام operationها را کنترل می‌کند؛ سند فعلی ۲۴ path دارد.
- سرور قدیمی که routeهای ابتدای توسعه را در حافظه داشت با `start-local.command`
  راه‌اندازی مجدد شد؛ Swagger واقعی اکنون تمام مسیرهای فازهای ۱ تا ۱۰ را نمایش می‌دهد.
- سایت و Swagger روی Tenant پاسخ 200 و همان API روی دامنه مرکزی پاسخ 404 دارد.
- چک‌لیست قدیمی فاز صفر با وضعیت واقعی تطبیق داده شد. فقط تست دو Tenant واقعی و تست
  یکپارچه Android/iOS با علامت توقف و وابستگی محیطی باقی مانده‌اند.
